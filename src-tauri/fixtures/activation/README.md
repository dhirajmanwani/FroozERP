# Offline-activation fixtures — TEST MATERIAL ONLY

Stage 3 of `docs/offline-activation-plan.md`. Everything in this directory is signed with
**deliberately public throwaway keys** and exists to drive
`src-tauri/tests/activation_roundtrip.rs`.

## The keys in this directory are not secret and are not the product keys

`TEST-ONLY-root-key-alpha.hex` and `TEST-ONLY-root-key-bravo.hex` hold 32-byte Ed25519 seeds whose
bytes are literal ASCII:

```
alpha  "FROOZERP TEST ONLY KEY ALPHA 001"
bravo  "FROOZERP TEST ONLY KEY BRAVO 002"
```

Hex-decode either file and you get that sentence back. They are committed on purpose, they are
worthless, and nothing in the shipped application trusts them —
`entitlement::TRUSTED_ACTIVATION_KEYS` still holds Stage 1's placeholder material and is
**untouched by Stage 3**. The round-trip tests pass their own trusted-key table, which is exactly
why `verify()` takes it as a parameter.

**The real root keypair is generated by the maintainer, on the maintainer's own machine, and never
enters this repository** (design §3.3, D-3). It was not generated during Stage 3.

### Generating the real keypair, when the time comes

The signing CLI does not generate keys — a key minted on a cloud build host would violate §3.3 no
matter how carefully it were handled. Produce 32 random bytes locally, then read the public half
out:

```powershell
# Windows / PowerShell
$b = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
[IO.File]::WriteAllText("$HOME\froozerp-root-key.hex", -join ($b | % { $_.ToString('x2') }))
```

```sh
# anywhere with openssl
openssl rand -hex 32 > ~/froozerp-root-key.hex
```

```sh
sign_activation pubkey --key ~/froozerp-root-key.hex --key-id 1
```

`pubkey` prints the public key as hex on stdout and, on stderr, the exact
`(0x01, [ ... ])` literal to paste into `TRUSTED_ACTIVATION_KEYS`. Do that twice — D-2 requires two
populated slots (`current` and `next`) at first release. Store the private files per D-3: encrypted
on the maintainer's machine plus a separate paper backup, with a passphrase distinct from the
release signing password named in `CLAUDE.md`.

## Why the fixtures live here

`src-tauri/fixtures/` is a sibling of `src-tauri/migrations/`, the existing precedent for non-Rust
assets that belong to the Rust crate. Three properties made it the choice:

- It is **outside `src/`**, so nothing here can be swept up by cargo's module or binary
  autodiscovery, and nothing here needs a `#[cfg(test)]` guard to stay out of the build.
- It is **not listed in `tauri.conf.json`'s `bundle.resources`**, so none of it reaches the
  installer.
- It sits next to the crate whose tests read it, so `CARGO_MANIFEST_DIR` locates it without any
  build script or path plumbing.

## Fixture inventory

All fixtures are `company_id = 1`, `branch_id = 1`, `key_id = 1` (except where noted), signed by
**alpha** (except where noted), and bound to device `FZDEV-TEST-0000000000001` (except where
noted). Day-stamps are days since 2020-01-01. The suite evaluates every fixture at
**day 2420 (2026-08-17)** with `now == high_water`.

Each fixture is three files: `<name>.lic` (the §7.2 container), `<name>.payload.bin` (the exact
signed bytes) and `<name>.sig.bin` (the detached signature).

| Fixture | What is different | Expected result at day 2420 |
| --- | --- | --- |
| `valid` | nothing — the reference artefact | verifies; binding OK; `Active` |
| `grace` | issued day 2000, 365-day validity → expires 2365, grace to 2425 | verifies; `Grace` |
| `expired` | issued day 1000 → grace ended day 1425 | verifies; `Expired` |
| `wrong-key` | declares `key_id 1` but is signed by **bravo** | `RejectReason::BadSignature` |
| `unknown-key-id` | `key_id = 0x7F`, absent from the trusted table | `RejectReason::UnknownKeyId { found: 0x7F }` |
| `wrong-device` | bound to `FZDEV-TEST-0000000000002` | verifies; `check_device_binding` → `DeviceBindingMismatch` |
| `bad-format-version` | `format_version = 9` | `RejectReason::UnknownFormatVersion { found: 9 }` |
| `truncated-signature` | 63 signature bytes | `RejectReason::TruncatedSignature { found: 63 }` |
| `bootstrap` | carries an Owner credential, 30-day window (expires day 2430) | verifies; `Active`; credential present and still open |
| `bootstrap-expired` | same, 7-day window (expired day 2407) | verifies; **still `Active`**; credential window closed |

Two of these are worth reading twice:

- `wrong-device` **verifies**. Signature validity and device binding are separate questions and
  fail separately, so a genuine code delivered to the wrong branch is never reported as a forgery.
- `bootstrap-expired` is **still `Active`**. §8.2 makes the bootstrap window a different clock from
  entitlement validity; an expired temporary password must never take a shop out of `Active`.

## Regenerating

The tests regenerate every fixture on each run into `CARGO_TARGET_TMPDIR` and compare byte-for-byte
against what is committed here. Ed25519 signing is deterministic (RFC 8032 §5.1.6) and the `.lic`
header carries no wall-clock timestamp, so any difference is a real change in the format.

After an intentional format change:

```sh
FROOZERP_REGENERATE_ACTIVATION_FIXTURES=1 cargo test --manifest-path src-tauri/Cargo.toml
```

The argument vectors live in `catalogue()` in `src-tauri/tests/activation_roundtrip.rs` — that
function is the single source of truth for how each fixture is minted.
